# 無人観測レポート 設計メモ（プラン・規約・将来連携）

この文書は `feature/unattended-observation-report` の設計判断を記録する。
実装本体は `core/observation_sessions.py`、`core/unattended_report.py`、
`core/report_export.py`、`core/report_ai.py`、`ui/pages/unattended_report.py`。

## MVP範囲の調整（理由付き）

1. **セッション開始・終了はレポート画面から明示操作する。**
   Battle Hunter / Top固定観測 / TopWatch は別プロセス・別プロファイルで
   動作しており、それらの開始経路すべてへ自動フックを差し込むと収集本体の
   変更範囲が大きくなる。既存の `collector_health.json` ハートビートを
   サンプリングして「実際に監視できた時間／接続中断」を実測する方式にしたため、
   収集コードには一切手を入れていない。将来、各コレクタの開始・停止地点から
   `SessionStore.start_session/stop_session` を呼ぶ配線を追加できる。
2. **TopWatch 子プロセスのデータは読み取り専用で参照する。**
   `top_watch/<streamer_id>/.../capture_fixed` の配置が「フォルダ名＝観測対象」を
   検証できる場合のみ集計対象に含めた（`available_sources`）。セッションの
   開始・停止は子プロセス側の責務とし、親画面からは操作しない。
3. **PDF のグラフは代表バトル方式。**
   全バトルのグラフを PDF に並べるとページ数が膨らむため、視聴者サンプル数が
   最多のバトルを「代表バトル」と明記して掲載する。全バトルの推移はアプリ内
   「推移」タブと JSON で確認できる。

## 観測セッション設計

- 保存先は分離: `<capture>/observation_report/sessions.sqlite3`。
  既存の battles DB には書き込まない。
- 異常終了・停電時は、次回起動時に `running` のまま残ったセッションを
  `interrupted` として検出する。終了時刻は推測で確定させず `ended_at` は
  NULL のままにし、最後の heartbeat 時刻を証拠として保持する。
- 復旧判定の安全ガード: セッションには所有プロセスのトークン
  （`owner_token`）を持たせ、自プロセス所有のセッションは絶対に復旧対象に
  しない。他プロセス所有でも heartbeat が新鮮（既定180秒以内）な間は
  復旧しない。`refresh()` のたびに復旧が走っても生存中のセッションは
  中断扱いにならない。
- セッションの寿命は UI 画面ではなくプロセス側の `SessionRuntime`
  （capture ディレクトリ単位のシングルトン）が持ち、サンプラーは
  ランタイムが所有する。レポート画面を切り替えても記録は継続する。
- セッション終了時はランタイムがバックグラウンドで JSON レポートを
  自動生成する（失敗しても収集・終了操作に影響しないベストエフォート）。
  画面での集計、PDF 出力、AI 分析は手動操作のまま。
- 監視できた時間は heartbeat サンプルの実測累積。サンプリング間隔を
  超えた空白は `gap_seconds`（不明）として分離する。
- TopWatch の実保存先は `top_watch/<配信者ID>/AI-TikTok-LIVE-Analyzer/capture_fixed`
  （子プロセス自身の LOCALAPPDATA 相当ツリー）。`available_sources()` は
  この階層を最優先で探し、旧来のフラットな配置もフォールバックとして残す。

## プラン別機能制御（設計のみ・未有効化）

`core/report_plans.py` に機能キーと想定プランの対応を定義した。
現段階では enforcement は既定 OFF で、すべての機能が利用できる。
課金判定・決済は今回のスコープ外。

| 機能キー | 内容 | 想定プラン |
|---|---|---|
| report.basic | 基本統計レポート | Free |
| report.charts | スコア・視聴者数グラフ | Free |
| report.json_csv | JSON / CSV 出力 | Free |
| report.pdf | PDF出力 | Pro |
| report.compare | 前回レポートとの比較 | Pro |
| report.ai | AI改善提案 | Pro |
| report.multi_streamer | 複数配信者の比較レポート | Agency（将来） |
| report.agency_rollup | 事務所向け集計 | Agency（将来） |

既存のライセンス認証（`core/license_client.py`）の仕様は変更していない。
将来プラン判定を入れる場合は、ライセンスサーバーの応答にプランを含め、
`feature_allowed()` の呼び出し側でだけ制御する想定。

## Phase 1（Pulse Pro）: 「配信レポート」へのUI改修（2026-10-30）

画面名を「無人観測レポート」から「配信レポート」に改め、ライバー本人が
配信後に振り返る流れに再設計した（`ui/pages/unattended_report.py`）。

- ヘッダー: 観測対象・状態（観測中/終了/中断）・開始時刻・経過時間と、
  主要操作「分析を開始 / 分析を終了 / レポートを表示」。
  対象データ（バトルと同時視聴者数の観測記録であり、音声・発言は含まない）
  を明示し、「分析」の誤認を防ぐ。
- 概要タブ: KPIカード8枚（観測時間、記録バトル数、正常終了バトル数、
  最大確認スコア、スコア中央値、視聴者数中央値、最大確認視聴者数、
  データ取得状況）を大きな数値で表示。未取得は0にせず「未取得」。
- グラフ: 選択バトルのスコア推移と同時視聴者数推移を併記。
  未取得区間（値が None の点）は従来どおり線をつながない。
- バトル履歴タブ: テキスト羅列を廃し、一覧行（配信者・日時・形式・
  最終スコア・視聴者数・終了状態）＋「詳細」で概要のグラフへ移動。
- AI改善提案タブ: 回答を 観測結果の要約 / 良かった傾向 /
  改善を検討したい点 / 次回の配信で試すこと に分けて表示。
  区分できない回答は無理に分割せず全文をそのまま表示する。
  実行は従来どおり明示ボタンのみ。
- レポート出力タブ: PDF / CSV / JSON を集約。PDF・AIが手動であること、
  セッション終了時のJSON自動生成が維持されることを明記。
- 詳細設定タブ: データ種別（通常観測／固定観測／TopWatch）、観測モード、
  セッションID、配信者ID検索、期間指定、集計範囲、用語定義を集約。
  既存機能は削除していない。TopWatchは読み取り専用のまま。
- 共通部品: 空ファイルだった `ui/components/stat_card.py` /
  `section_card.py` / `status_badge.py` を実装し、本画面で使用。
  KPI・一覧・グラフの構造は将来の Pulse Agency 画面でも再利用できる形にした。
  Agency のログイン・所属管理・クラウド同期・同意管理・テナント分離・
  課金は今回実装していない（認証・権限基盤の整備後に行う）。
- セッション管理（SessionRuntime）、58件の既存テスト、終了時JSON自動生成、
  スコア取得方法、SQLiteスキーマには変更なし。

## Phase 2（Pulse Pro）: 固定観測の標準化（2026-10-30）

個人ライバーが自分の @ID を一度登録すれば配信分析を始められるよう、
既存の固定観測（top_viewer.py の方式）をアプリ本体へ標準搭載した。
新規ブランチ `feature/pulse-pro-fixed-observation`（PR #8 のブランチを
ベースにした積み重ね型）で実装し、PR #8 自体は変更していない。

- アカウント設定: `core/fixed_observation.py` が settings.json の
  `pro_tiktok_id` に登録IDを保存し、次回起動時に復元する。ID変更も可能。
  本人確認は未実装であり、登録IDは「観測対象の設定」と明示する。
  認証済み所有者とは一切表示しない。
- 収集プロセス接続: 「配信分析を開始」は、登録IDの LIVE URL を
  `LIVEMETRY_FIXED_URL`、`LIVEMETRY_OBSERVATION_MODE=fixed` を環境変数に
  設定して既存コレクタ（core/viewer_collector.py）を子プロセスとして
  起動する（top_viewer.py と同一方式、`fixed_target.json` も同形式で記録）。
  固定モードではコレクタ自身が Battle Hunter の自動スクロールを無効化し、
  保存先は `capture_fixed`（別プロファイル・別DB）で `capture` と混ざらない。
- 配信レポート統合: 画面の初期データ種別を固定観測にし、セッションは
  登録IDを対象（targets=[登録ID]）として開始するため、他ライバーの記録が
  本人のセッション成績に混ざらない。終了時のJSON自動生成は従来どおり
  SessionRuntime が行う。PDF・グラフ・AI改善提案は Phase 1 の画面を再利用。
- 状態表示: コレクタの heartbeat（collector_health.json）から
  観測中（接続中）／待機中（配信オフライン・未接続）／接続切れの可能性／
  接続制限／停止中 を区別して表示する。オフラインは異常として扱わない。
- プロセス寿命: FixedObservationController はプロセス全体のシングルトンで、
  画面遷移では停止しない。アプリ終了時（MainWindow.on_close）に停止する。
- 研究モードの保護: Battle Hunter・TopWatch・通常観測には変更を加えていない。
  Agency へのデータ共有は未実装（本人確認・同意・権限が別途必要）。
  ライバー単位の分離は、固定観測DB＋セッション対象IDで担保する設計。

## Phase 3: 3モード対応ワークスペース・サイドバー再設計（2026-10-30）

新規ブランチ `feature/pulse-workspace-navigation`（PR #9 のブランチを
ベースにした積み重ね型）。今回は画面構造とナビゲーションの分離のみで、
Agency 機能・認証機能は実装していない。

- 構成定義: `core/workspace_config.py` にモード（streamer / developer /
  agency）とモード別ナビゲーションを定義。ナビの遷移先は既存の
  MainWindow.show_* メソッド名で、存在しない画面（Challenge Investigator
  のUI、PR #7 の画面証拠、ログ画面、Agency の全画面）は項目に含めない。
- 状態管理: `core/workspace_manager.py` が settings.json の
  `workspace_mode` と `developer_mode_enabled` を管理する。
  初期モードはライバー。開発者モードは設定画面の「開発機能を表示」を
  有効にしたときだけ選択可能。保存値が利用不能・不正な場合はライバーへ
  戻す。これは表示設定であり、ライセンス認証や権限とは無関係。
- Agency: `agency_available()` は常に False（将来はサーバー側の権限
  情報で決める）。サイドバーには「準備中」の注記のみで、選択肢・画面・
  架空データは作らない。ライセンスプランの表示だけで Agency を
  有効化することはない。
- サイドバー: ロゴの下にワークスペース選択欄を置き、モード切替で
  ナビ項目を再構築する。ナビはスクロール可能な枠にして、720p や
  表示倍率 125%/150% でも全項目へ到達できるようにした。設定は
  どのモードからでも下部のボタンで開ける。モード切替時は安全な
  ホーム（Dashboard）へ遷移する。
- ライバーメニュー: ホーム / ライブ画面 / 配信レポート / バトル分析 /
  成長記録（Analytics）/ AI改善提案。履歴は従来どおり Dashboard の
  最新結果パネルから開ける。
- 開発者メニュー: ダッシュボード / TikTok Viewer / 収集状況 /
  収集履歴 / 収集分析 / バトル分析 / 観測レポート / 履歴 / Analytics /
  AI分析（いずれも既存画面）。
- 互換性: モード切替はナビ再構築とホーム遷移のみで、コレクタ・
  SessionRuntime・固定観測プロセスには一切触れない。そのため観測
  セッションはモード切替後も継続する。通常 Viewer の自動起動と固定
  Viewer は従来どおり別プロファイル・別DBで共存する設計
  （top_viewer.py 併用時と同じ）。二重起動でデータが混ざることは
  ないが、Viewer ウィンドウが2つ開く負荷面の整理は今後の課題。

### Phase 3 レビュー修正（2026-10-30）: 開発機能トグルの即時反映

設定画面の「開発機能を表示」は保存されていたが、MainWindow 側の同期
（sync_workspace_from_settings）が設定画面表示直後の単発タイマーからしか
呼ばれず、トグル操作がサイドバーへ即時反映されなかった。修正として、
SettingsPage がトグル変更の瞬間に MainWindow のコールバックを呼ぶ方式に
変更した（コールバック内では after(0) で現在のイベント処理の完了直後に
同期し、設定画面がハンドラ途中で破棄されないようにしている）。定期
ポーリングは追加していない。OFF にした場合は、開発者モード使用中でも
即座にライバーモードへ戻る。GUI 回帰テストは
tests/workspace_gui_test.py（G1–G10）。

### 未解決事項（管理対象）: 固定観測の二重起動と観測対象ID

PR #9 から引き継いだ既知のリスクで、Phase 3 でも未解決のまま管理する。

1. 二重起動: 本体の通常 Viewer は起動時に自動起動する一方、固定観測は
   別プロセスの固定 Viewer を起動する。両者は別 WebView2 プロファイル・
   別DB（capture / capture_fixed）のためデータ混在はないが、Viewer
   ウィンドウが2つ開き、CPU・メモリ負荷が増える。また top_viewer.py を
   並行使用すると、同じ capture_fixed プロファイルに対して固定コレクタが
   二重に起動し得る（top_viewer.py 側の fixed_viewer.lock を本体側
   コントローラは確認していない）。
2. 観測対象IDの不一致: 固定観測の実行中に登録ID（pro_tiktok_id）を
   変更しても、実行中のコレクタとセッションの対象は開始時点のIDのまま
   （変更は次回開始から反映、と画面にも明記）。そのため「現在の登録ID」と
   「実行中セッションの対象ID」が一時的に食い違う状態があり得る。
   レポートのセッション対象はセッション側の targets を正とする。

いずれも対策の実装は未着手であり、修正する場合は別途仕様確認を行う。
