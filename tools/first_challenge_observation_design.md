# Livemetry Pulse ファーストチャレンジ観測設計（フェーズD）

- 作成日: 2026-10-28
- 位置づけ: `Livemetry-Pulse-ファーストチャレンジ-観測基盤.md`（probe v2 が GiftMessage を保存すること、および 2026-10-24 の未保存は v2 以前のビルドが原因であることを確定）の続編。本書は差分と観測設計のみを扱い、既存レポートの内容は繰り返さない。
- 前提（確定済み・変更なし）: ファーストチャレンジ専用のイベント／フィールドは取得可能なデータ内に存在しない。スコア増分比は倍率の出所を同定できない。正式な自動検出は実装しない。判定は CONFIRMED / CANDIDATE / UNKNOWN の3段階で、CONFIRMED は画面側の正解データとの照合が必須。

## 2. 観測の目的

自動検出の可否を、推測ではなく **画面表示と WebSocket イベントの対応表** で決めること。具体的には次の3問に答えるための正解データを集める。

- Q1: `WebcastBattleGameplayMessage` が届いた瞬間、画面には何が表示されていたか（ファーストチャレンジ×3表示の有無とその文言・倍率）。
- Q2: ファーストチャレンジ×3が表示されたバトルで、GameplayMessage は必ず届くか（取りこぼしの有無）。届く場合、表示開始・終了と受信時刻のずれはどれだけか。
- Q3: GameplayMessage が届いても×3が表示されないバトルはあるか（誤検出側の反例）。

Q1〜Q3 が複数バトル（1v1／3人／2v2 を含む）で埋まって初めて、検出条件の検討に進める。1件の一致では進めない。

## 3. 同期設計（画面⇔WebSocket）

### 3.1 同一 PC・同一時計を基準にする

- ログ側の時刻は probe の `received_at`（監視 PC のローカル時刻、エポック秒）で既に記録されている。画面側も **同じ PC 上で録画** すれば、時計のずれは原理的に発生しない。これが最も強い同期手段であり、外部時計や別デバイス録画は使わない。
- ただし「録画フレームに写った表示」と「イベント受信」の間には、描画遅延・録画のフレーム間隔ぶんの不確かさが残る。設計上は **±2秒の不確かさ区間** として扱い、1秒未満の一致を主張しない。

### 3.2 ミリ秒時計を画面内に写し込む

- 観測中は、ミリ秒表示の時計ウィジェット（同一 PC の時計を読む小さなオーバーレイ、またはブラウザタブ）を TikTok 表示と同じ画面内に常時表示し、録画・スクリーンショットに一緒に写るようにする。
- これにより、後から録画を見たときに「×3表示が出た瞬間の PC 時刻」をミリ秒単位で読み取れる。読み取った時刻と probe の `received_at` を突き合わせれば、表示→受信の遅延分布も測れる。
- 時計の取得方法は問わない（OS 標準時計の秒表示では不足なので、ミリ秒が出るものを使うこと）。重要なのは **probe と同じ PC の同じ時計** であること。

### 3.3 アンカーイベントで相互検証する

- ギフト送信・バトル開始など、画面とログの両方で時刻が特定できる事象をアンカーとして記録する（例: バトル開始は LinkMicBattle の server start_time_ms と画面のカウントダウン）。
- アンカーで測ったずれが ±2秒に収まらないセッションは、そのセッション全体を照合対象から外す（時刻が信用できないデータを混ぜない）。

### 3.4 記録フォーマット

観測セッションごとに、次の対応表を手作業または半自動で残す（ツール化は §5）。

| 項目 | 内容 |
|---|---|
| session_id | 観測日時ベースの一意な ID |
| battle_id | ログ側の payload 確定 battle_id（時刻窓で推定した ID は使わない） |
| display_start / display_end | 画面で×3表示が出ていた区間（ミリ秒時計の読み取り値、JST） |
| display_text | 画面の文言と倍率（目視記録。そのまま転記し、解釈しない） |
| gameplay_received_at | GameplayMessage の受信時刻（investigator の出力から） |
| task_summary | 同時刻帯の TaskMessage の分類（tracker 互換分類と未分類理由） |
| anchor_offset_seconds | アンカーで測った画面⇔ログのずれ |
| verdict_for_session | 表示あり／表示なし／判定不能 のいずれか（目視の事実のみ） |

- 時刻はすべて JST（Asia/Tokyo）で記録し、エポック秒も併記する。
- 個人情報は記録しない: 配信者・視聴者の名前、@ID、コメント本文、Cookie・セッション情報は対応表に入れない。残すのは battle_id、時刻、表示文言、イベント種別だけ。

## 4. 録画・スクリーンショットの設計（オプトイン専用）

### 4.1 原則

- **ユーザーが明示的に有効にした場合のみ** 動作する。既定は無効。アプリの通常動作（収集・監視）に録画機能を結び付けない。
- 画像・動画は **ローカル保存のみ**。GitHub へのアップロード、外部送信は一切しない。
- 録画しなくても §5 の事後照合（手動の時刻読み取り）が成立する設計にし、録画は「読み取りを楽にする補助」と位置づける。

### 4.2 方式の候補（負荷の小さい順）

1. **静止画の間引き保存（推奨の第一候補）**
   - 観測モード中だけ、既存のフレーム取得（latest.jpg の仕組み）を流用し、1〜2秒間隔でフレームを保存する。×3表示は数十秒続く想定のため、1〜2秒間隔で表示区間の特定には足りる。
   - 保存先は観測セッション専用フォルダ。1セッション上限（例: 500MB）を決め、超えたら古い順に間引く。
   - 動画より桁違いに軽く、後から「表示が出たフレーム／出ていないフレーム」を時刻で並べられる。
2. **OBS 録画（ユーザーが既に OBS を使う場合のみ）**
   - ユーザーは現在 OBS を使用していない（設定キーだけが存在し、呼び出し経路はない）。新規に OBS 連携コードは書かない。ユーザーが手動で OBS 録画する場合は、ミリ秒時計の写し込み（§3.2）だけ守れば同じ照合ができる。
3. **OS 標準の画面録画（Game Bar 等）**
   - 手動運用の選択肢。コーデックや保存先は OS 任せでよいが、ファイルが大きくなりがちなため長時間観測には向かない。

### 4.3 負荷・容量の目安

- 静止画方式: 1280×720 の JPEG（約100〜200KB）を1.5秒間隔で保存すると、1時間あたり約240〜480MB。上限設定と自動間引きを必須とする。
- 録画・保存の処理は収集（WebSocket 受信・probe 記録）と同一スレッドで直列化しない。保存に失敗しても収集は止めない（観測基盤レポートで確認した probe の「失敗しても監視を止めない」方針と同じ）。
- バトル観測そのもの（Battle Hunter / TopWatch）の動作には干渉しない。観測モードは固定観測（capture_fixed）での利用を基本とし、巡回観測と同時には使わない。

## 5. 事後照合ワークフロー（自動検出できない場合の本命）

自動検出が成立しなくても、後から「あのバトルの×3表示はログのどのイベントに対応するか」を再構成できることを優先する。

1. **観測する**: probe v2 で通常どおり収集しつつ、§4 の方式で画面を残す（ミリ秒時計を写し込む）。対象は 1v1／3人／2v2 を最低1件ずつ、×3表示が出たバトルと出なかったバトル（ボーナスのみのバトルを含む）の両方。
2. **エクスポートする**: そのセッションの probe JSONL（ローテーション .1〜.3 を含む）と画面素材を1フォルダにまとめる。生ログと画像は GitHub に上げない。
3. **解析する**: `tools/first_challenge_investigator.py` に JSONL を渡し、GameplayMessage の発生時刻・同時受信イベント・前後90秒の GiftMessage・TaskMessage の分類理由を JSON／CSV で得る。
4. **照合する**: §3.4 の対応表に、画面で読み取った表示区間（ミリ秒時計）と investigator のイベント時刻を並べ、アンカーずれで補正して記入する。表示とイベントの対応は **目視で確認できた範囲だけ** を書く。対応が取れないイベントは「対応なし」と明記する（無理に対応付けない）。
5. **蓄積する**: 対応表だけを残し、画像は確認後に削除してよい（容量節約）。対応表が増えたら Q1〜Q3（§2）を集計し、GameplayMessage の感度・特異度を数える。
6. **判断する**: 表示あり全件で GameplayMessage が先行／同時であり、表示なし件で届いていない、という対応が複数形式で再現した場合に限り、検出実装（開始・終了・倍率の記録とグラフ表示）の設計に進む。倍率は画面表示またはイベント内の明示フィールドでのみ確定し、スコア増分からは推定しない。

## 6. 今回やらないこと

- GameplayMessage を根拠にしたファーストチャレンジの自動検出・断定表示（証拠不足）。
- OBS 連携コードの新規実装（ユーザーは OBS 未使用）。
- 録画機能のアプリ組み込み（本書は設計のみ。実装は観測で対応が取れた後の別フェーズとし、有効化はユーザーの明示操作を前提とする）。
- 過去データ（2026-10-24 の capture_fixed エクスポート等）の再解析による確定判定。当該バトルは画面記録が無く、遡って CONFIRMED にはできない。

## 7. 次に必要なデータ

1. ×3表示が出たバトル **3件以上** の、ミリ秒時計入りの画面記録と同一セッションの probe JSONL（1v1／3人／2v2 を含む）。
2. ×3表示が出なかったバトルの対照記録（通常バトル、ボーナスミッションのみのバトル）。
3. GameplayMessage が届いたのに×3表示が無かった事例（あれば最重要の反例）。
4. 各セッションのアンカーずれ（§3.3）の実測値。

これらが揃うまでは、GameplayMessage は CANDIDATE のままとし、判定は UNKNOWN を維持する。
